自测时让 Agent 修 bug，有一种改法让我很别扭。

一个需求，方案讨论完，代码写完，部署到自测环境。测出 bug 了，回头让 Agent 修。这个时候，它有时会开始考虑“兼容旧代码”：原字段留着，新字段再加一个；原逻辑不能删，于是旁边补一条分支。

可那些所谓的旧代码，就是这个需求刚写出来的东西。还没正式上线，也没有人依赖，直接改掉就行。

这件事也不只发生在 AI 写的代码上。我手写了一部分，再交给 Agent 修，它同样可能把眼前已经存在的实现当成需要保护的历史行为。修复本来可以顺便删掉一段错误实现，结果代码反而更多了。

我想找一个办法，让 Agent 在动手之前知道：这个需求走到哪一步了，哪些东西可以直接改，哪些确实有人在用。

## “旧代码”到底有多旧

拿字段改名举个例子。下面是示意，并非某个项目的实际代码。

新需求里加了一个 `type` 字段，自测时发现它的含义不准确，应该改成 `category`。如果定义和调用都在本轮需求里，数据也不需要保留，修复应该把相关位置一起改掉。

Agent 却可能留下这样的处理：

```javascript
const category = payload.category ?? payload.type;
```

单看这一行，很合理。放回这个需求里，就要问一句：谁还在传 `type`？

能指出一个已经发布的客户端，兼容就有来由。只说“上一轮代码里有这个字段”，这个理由就不够了。继续往下保留，很快还会出现两个字段的优先级、校验规则，以及两份都传时该听谁的测试。

一个本来可以直接改名的字段，多出了一组需要长期解释的行为。

我更愿意给兼容加一个具体要求：写之前，先说明依赖对象。哪个客户端、哪个服务、哪批必须保留的数据，还在使用旧行为？代码提交过、合并过、部署过，都不能单独回答这个问题。

## 实现完成以后，需求还在继续

Agent 说“开发完成”，通常是在结束当前这轮任务：实现已写好，该跑的检查也跑了。但开发者接下来还要部署、自测、改 bug、回归，最后才决定发布。

如果后续对话只剩一句“这个字段不对，改一下”，Agent 看到的就只有现有实现，很容易按维护既有功能的方式处理。

所以我想把两类信息分开记。

一类是开发进度：开发中、待自测、自测修复、待发布。另一类是实际使用情况：部署到了哪里，有没有生产流量，有没有独立调用方，是否产生了必须保留的数据。

这两类信息并不总是同步。需求还没验收，也可能已经有其他团队在联调；功能开关没开，也可能已经执行了数据库变更。进入自测阶段，也不能证明周围所有代码都可以随便改。

要判断的范围，是这次准备修改的字段、接口和逻辑。一个老项目里的新需求，当然仍然要照顾原来已经发布的行为。

## 先解决记录从哪里来

讨论时，一个很自然的方案是：给每个需求建一份状态文件，Agent 每次修复前先读它。

但这里有个前提，实际开发里经常不成立。我通常只会把需求或者方案发给 AI，让它设计、实现，并不会再补一句“请把需求保存下来”。手写代码时更不会为了等会儿让 AI 修 bug，先写一份状态记录。

还得由我先建文件、再更新状态的话，这套办法大概用不了几次。

因此，记录应该成为 Agent 开始开发时自动做的一件小事。接到需求后，先找有没有对应的记录；没有，就从当前对话里提取必要内容。等方案确定、实现调整或收到自测反馈，再维护同一份记录。

不需要把聊天全文搬进仓库。留下目标、修改范围、开发起点，以及目前知道的发布和依赖情况，就够开始了。

比如，一个新需求刚进入开发时，可以先留下这样的记录：

```yaml
id: order-category
goal: 为订单增加分类能力
scope:
  - 订单分类字段
  - 订单接口
  - 管理页面
start_commit: "开始开发前的提交 SHA"
stage: developing
deployment:
  environments: []
  production_exposure: unknown
  evidence: []
dependencies:
  external_consumers: unknown
  data_to_preserve: unknown
```

这里的 `unknown` 要保留。Agent 刚开始接手任务，未必知道发布情况，不能因为记录是新建的，就把代码都判成未发布。

`start_commit` 也只用来帮助定位本轮修改。它不一定是生产版本；如果开始时工作区就有未提交代码，还要记录相关文件或差异，不能简单用这个提交之后的全部变更代替需求范围。

以后我说“只部署到了自测环境，还没有进入生产”，Agent 就把这个事实记下来，并注明依据来自这次反馈。数据能不能丢、有没有别的服务接入，如果没说，仍然留待查证。

记录可以放在 `docs/changes/`，也可以接入团队已有的需求单。目录名字没有那么要紧，后续任务能找到、能更新，才有用。敏感业务数据和凭据不该跟着聊天一起落进仓库。

## 修 bug 时，继续接着这个需求做

有了记录以后，整个过程可以很平常。

我说“给订单增加分类，帮我设计并实现”。Agent 建立记录，设计和开发继续进行。它完成本轮实现时，把进度更新成待自测，发布情况沿用已有证据。

我部署后说“自测发现分类字段不对，换一个结构”。Agent 找到原来的需求，把进度改成自测修复，再看这次涉及的字段有没有实际依赖。

确认字段属于本轮新增、没有需要保留的调用或数据后，就统一改定义、调用和测试，把旧路径删掉。修完回到待自测。同一个需求可以在这里来回几次，无需每次都重新开一份记录。

换了聊天，记录就能帮助恢复背景。需求编号、分支和修改文件都可以辅助匹配，但一个分支里可能有多个需求，文件也可能被反复修改，不能只凭“最近的一份”就认定归属。找不准时，问一句“这是继续修订单分类需求吗”就够了。

对于我已经手写了一半的需求，也可以从 Agent 接手时补建记录。它能确认的内容先写下，无法从对话和代码中确认的发布信息，再针对性核实。Git 差异能说明改了什么，不能证明哪些代码已经被人使用。

## 规则负责提醒，Skill 负责具体步骤

我倾向于在项目入口规则里写一小段要求，提醒 Agent 在开始开发和修复时先关联需求。具体步骤和记录模板则放进一个专门的 Skill。

以 Codex 为例，[官方文档](https://learn.chatgpt.com/docs/agent-configuration/agents-md)说明，`AGENTS.md` 用于提供项目指令；[Skill 文档](https://learn.chatgpt.com/docs/build-skills)则介绍了显式调用和按任务描述匹配的加载方式。因为 Skill 要经过调用或匹配，我会把“先关联需求记录”放在入口规则里。

下面是一份拟议的规则，尚未作为完整工具实现或验证：

```text
收到需求设计、实现或修复任务时，先查找对应的需求记录。
没有记录时，从对话和代码探索中自动补建最小记录。
不要要求用户额外提出“记录需求”，也不要为常规记录动作增加确认。

记录目标、范围、开发起点、阶段、部署事实和已知依赖。
已确认事实应注明依据；未知信息保留为未知。
设计调整、实现完成、自测反馈和发布后，更新同一份记录。

实现完成、测试通过、提交、合并或部署到自测环境，
均不能单独作为需求已经发布或必须兼容的依据。

修改前区分既有已发布行为与本需求新增实现。
已确认没有保留义务的本轮实现，优先直接修正并删除废弃路径。
新增兼容逻辑时，说明依赖对象、证据以及移除条件。
发布和依赖情况不明时，先查证，再决定如何修改。
```

Skill 可以叫 `change-lifecycle`，在需求设计、开发、自测修复和发布反馈时使用。它需要做的事情也很具体：关联记录，更新已知事实，判断本次修改的依赖，再把处理结果写回去。

比如，结束修复时留下这样一句说明就够了：

> 本次调整涉及尚未发布的订单分类字段；调用方已同步修改，自测数据已确认无需保留，旧字段读取路径已删除。

确实要保留兼容，也写清楚原因：哪个已发布的客户端还在使用旧字段，等它升级到什么版本后可以删除。这样下次再读到这段分支，就不用重新猜。

单靠几段指令无法保证 Agent 次次执行。团队如果已经有需求系统和部署流水线，可以逐步把记录与实际发布结果关联起来。但起步时，我不会先做一套大系统，一份短记录加一条入口规则已经足够试运行。

## 自测环境也有需要留下的东西

这套规则要避免走向另一个极端：一听说“还没上线”，就把旧结构全删了。

自测环境里可能有需要保留的验证数据，联调方可能还在跑旧版本。数据库迁移如果已经执行过，直接修改原脚本，也不会自动修正现有数据库。要不要补迁移、是否允许重建环境，仍然得按实际情况处理。

这些都应该进入需求记录，成为具体约束。反过来，纯属本轮开发、没有使用者、也没有数据保留要求的错误实现，就没必要仅为它“曾经存在过”而留下一条兼容路径。

我会先拿这几种情况检查规则有没有用：未发布字段改名，原字段能不能删干净；已经发布的接口调整，调用方是否被识别出来；换一个聊天继续修复，能不能关联到同一个需求；只有一句“开发完成”时，发布状态会不会被擅自推进。

目前这还是一套准备尝试的工作方式，效果需要在实际需求里验证。我最想看到的变化很具体：自测发现一个可以直接修正的问题，Agent 把相关代码一起改对，删掉废弃实现，然后告诉我这次按什么依据处理。下次继续修时，这些依据还能找得到。
