## 经验留下来了，维护工作也跟着留下来了 {#agent-skill-memory-governance-opening}

假设 Agent 排查了一次告警查询超时，修好了问题，留下操作方法和几条根因记录。下一次遇到相似现象，先读这些经验，确实能少走弯路。

后来依赖升级，日志入口迁移，查询方式也变了。旧 Skill 还在指向原来的路径，记忆里的“这个接口不能改”却没有标明版本。新任务继续往知识库里添东西，最后还是得有人收拾。

如果维护全落到我身上，省下的开发时间就有一部分变成了整理知识库的时间。我希望 Agent 把这段工作也接过去。

[上一篇](./skill-lifecycle.html)讨论经验从候选到正式能力、再到归档的路径。这篇接着问：**谁负责让这条路径真正运转？** 我的答案是，Agent 生成的 Skill 和记忆，应当由 Agent 在授权范围内继续验证、修订和清理。

下面是一套希望落地的治理做法，沿用这次假设的超时排查来说明。现成工具提供了一些零件，完整的维护链仍需要项目接起来。

![Agent 在知识转盘上复核自己产出的 Skill 和记忆，任务结束后仍然继续维护。](../assets/agent-skill-memory-governance-illustrations/01-agent-maintains-knowledge.png)


</section>

<section class="story-scene" data-scene="把维护接进任务" markdown="1">

## 一次任务的交付，要包括知识的后续处理 {#写下来之后活还没完}

Agent 已经能主动提炼方法，也会在下一次任务里引用旧结论。维护责任应当跟着这种能力一起增加。

这次超时排查结束时，先搜索已有条目：有合适的方法，就补充；没有，再建立候选。然后留下证据、适用范围和准入判断。如果新结果推翻了旧结论，还要找出旧条目及其引用，一并处理。

下一次任务开始时也要做同样的核对。旧经验对应哪个版本、什么环境？条件对不上，就先标为待复核。生成一份记录只能说明经验被保存，后续能否使用还需要判断。


</section>

<section class="story-scene" data-scene="先分清产物用途" markdown="1">

## 方法、事实和调查现场，要用不同办法检查 {#skill-和记忆分别管什么}

先看这次排查留下了什么。定位、回放和验证的方法，将来还要执行，适合整理为 Skill；根因、数据规模和方案取舍，是带条件的事实，适合放进记忆；查过哪些日志、试过什么方向，则先保留在任务记录里。

{% include story/graphic.html key="governance-roles" %}

三类产物的检查重点不同。仍用前面的假设案例：

| 产物 | 留下什么 | 以后检查什么 |
| --- | --- | --- |
| 项目 Skill | 定位查询、构造回放样本、验证修复的方法 | 步骤能否执行，是否误触发，验证有没有漏项 |
| 项目记忆 | 某次慢查询的根因、数据规模、方案取舍 | 证据能否找到，结论是否仍适用于当前版本 |
| 任务记录 | 查过的日志、试过的方向、执行过的命令 | 哪些证据值得保留，剩下的何时清理 |

Skill 可以引用记忆，记忆也可能包含操作经验。分类是为了选对验法，没有必要把互相关联的内容硬拆开。

![操作手册说明怎么做，证据夹记录事实及其成立条件。](../assets/agent-skill-memory-governance-illustrations/02-skill-and-memory.png)

[Agent Skills 规范](https://agentskills.io/specification)说明了 `SKILL.md`、脚本和参考资料的组织方式；[Claude Code 的记忆机制](https://code.claude.com/docs/en/memory)提供跨会话保留经验的能力。保存和读取有了入口，项目还要补上“现在是否仍然适用”的判断。


</section>

<section class="story-scene" data-scene="先作为候选验证" markdown="1">

## 一次修复成功，只够成为待验证的候选 {#新经验先放候选}

查询修改后变快了，未必已经证明根因。缓存是否预热、数据量是否变化、并发是否相同，都可能影响结果。没有对照的部分继续写作假设。

先给候选登记身份：标识、版本、范围、来源任务和证据位置，再推进状态：

```text
任务产生线索 → 候选 → 验证 → 生效 → 使用与反馈
                       ↑               ↓
                       └── 修订、合并 ──┘

发现前提变化 → 待复核 → 恢复使用 / 归档 → 按策略删除
```

这些状态需要接到实际的发现和检索机制。只往文件里加一个 `status: archived`，并不能保证工具停止加载它。

候选阶段也要克制。“接口为什么保留旧字段”值得记，因为代码通常解释不了当年的取舍；“某个类在哪个目录”随手就能查到，没必要再维护一份容易过期的副本。一次测试环境临时不通，留在任务记录里也许就够了。

真正进入验证时，沿着刚才的用途分别检查。

Skill 要试着执行。Agent 可以在隔离环境重现问题，拿历史样本回放，还要试几个相近但不适用的任务。普通网络抖动也触发了查询优化 Skill，就说明触发条件写宽了。

记忆要核对事实和条件。哪个版本、什么环境、用了哪些数据，证据支持到哪里，就写到哪里。查不到的部分保留为待验证，别为了让记录完整而补一个听起来合理的结论。

改了 Skill 的关键步骤，就重新跑对应验证；扩大记忆的适用范围，也要补新证据。旧版本那次通过，不能一直沿用。


</section>

<section class="story-scene" data-scene="按风险与授权分流" markdown="1">

## 先明确权限，Agent 才能把日常维护做完 {#入库不必每条都等人点头}

所有候选都等人逐条确认，维护最终还是会回到人手上。我更愿意预先确定哪些动作已获授权，以及各自怎样验收。

整理任务记录、清理重复索引、标记失效内容，可以成为日常维护。证据完整、范围明确的低风险记忆，也可以在这份授权内入库。

{% include story/graphic.html key="governance-entry" %}

会改变默认工作方式的 Skill 更新，需要回归用例、旧版对照和回滚办法，同时仍须属于已授权范围。扩大工具权限或改变发布流程，则要交给有权作决定的人。

权限要落在工具配置、仓库权限和 CI 上。只在说明里写“不要越界”，拦不住一次实际操作。

记忆也不能给自己发权限。“上次允许发布”是一段历史，下次能否发布，要看当前任务和有效的授权。网页或日志里夹带的指令，即便被存进记忆，也不能因此变成项目规则。

边界明确以后，范围内的维护就应该完整执行，不必每整理一张索引卡都重新确认。


</section>

<section class="story-scene" data-scene="回到当前现场" markdown="1">

## 历史根因是排查线索，不是本次结论 {#旧经验要拿到现场再看一遍}

仍用这次假设的排查。记忆里写着：“告警查询超时曾由深分页导致。”它可以提醒 Agent 检查当前请求，却不能直接把本次根因也定成深分页。

先按项目、模块和任务缩小范围，再核对版本、环境与失效条件。如果查询方式已经变了，旧结论保留在历史里，退出当前版本的默认建议。

暂时访问不了证据，则是另一回事：标记尚未复核，等条件具备再查。查不到和查证为错，不能混为一谈。

多数任务只需要几条相关经验。把整个知识库都塞进上下文，既增加阅读负担，也给过期条目更多干扰判断的机会。


</section>

<section class="story-scene" data-scene="让使用结果驱动修订" markdown="1">

## 记录哪一步有效，才能修对原来的经验 {#用完以后留下具体反馈}

被读取，说明条目被搜到了；任务完成，说明问题最终解决了。两者都不能单独证明这份 Skill 有效，Agent 也可能放弃了原步骤才找到办法。

我需要的反馈具体到执行环节，例如：

```text
使用对象：alarm-query-troubleshooting，版本 3
触发原因：告警检索 P95 延迟升高
执行结果：回放步骤有效；旧日志路径已失效
记忆核对：历史上的深分页结论不适用于本次请求
维护动作：修订日志定位步骤；补齐旧记忆的适用条件
```

这份记录是示意。真正使用时，还要能追到任务、代码版本、输入条件和证据。这样，维护者才知道应修改日志路径，还是复核根因判断。

{% include story/graphic.html key="governance-loop" %}

![Agent 根据实际执行结果修补原来的条目，把证据和修订一起留下。](../assets/agent-skill-memory-governance-illustrations/03-feedback-repairs-knowledge.png)

某一步连续失败，就检查脚本、环境和前提；用户纠正了结论，就找出引用它的地方；一条记忆被当前证据推翻，就重新评估它的范围。这些都能由任务直接触发，不必攒到月底再整理。

使用次数可以帮助挑出要复核的内容，却不能单独决定去留。低频的故障恢复流程，可能很久才用一次，删早了更麻烦。


</section>

<section class="story-scene" data-scene="沿着引用一起维护" markdown="1">

## 合并内容时，也要处理条件和引用 {#重复的合并冲突的查证}

每次排查都新建文件，超时相关 Skill 很快就会有四五份。合并之前，要比较触发条件、步骤和验法；名字相近，不代表解决的是同一种问题。

记忆合并也要保留条件。测试环境的结果和生产环境的结果，可以互相引用，未必能压成一句统一结论。

遇到冲突，先查版本和范围。例如：

```text
旧记忆：查询必须经过兼容层。
新证据：新版本已移除兼容层，迁移验证通过。

维护动作：
1. 给旧记忆补齐适用版本。
2. 更新当前版本的结论及证据。
3. 修订仍在引用旧路径的 Skill。
4. 让当前版本的默认检索退出旧结论。
```

新记录的时间更晚，证据不一定更强。如果版本和范围仍解释不了冲突，就保留两边依据，把剩余分歧交给人。

这里还有个容易漏的活：处理引用关系。记忆被推翻，相关 Skill 要复核；Skill 退出了，入口索引也要更新。只改正文，其他地方继续引用旧结论，这次维护就没做完。


</section>

<section class="story-scene" data-scene="同步发现与检索入口" markdown="1">

## 退出当前使用，要同步撤掉发现和检索入口 {#归档了就得真正退出检索}

当项目升级依赖、迁移模块或删除接口，Agent 应沿着条目的依赖关系做定向复核，核对路径、版本和证据。这比单看“多久没使用”更能说明当前适用性。

复核日期到了，表示该检查了。前提确实变了，才说明原结论可能不再适用。别把“太久没看”直接当成“已经过期”。

确认退出后，归档文件只是其中一步。入口索引、检索结果、派生内容和其他 Skill 的引用也要跟着更新。向量检索还在返回旧内容，当前任务就仍然可能沿着旧方法走。

![旧条目从当前索引退出，历史证据仍保存在归档中。](../assets/agent-skill-memory-governance-illustrations/04-archive-and-retrieval.png)

归档时保留替代条目、退出原因和必要的证据，方便以后回查。物理删除则按项目的数据保留策略处理，正文、附件、缓存、派生索引和历史副本都要纳入范围。需要恢复的旧内容，也得先复核再重新生效。


</section>

<section class="story-scene" data-scene="在一次任务中闭合" markdown="1">

## 交付任务时，把知识的变化也交代清楚 {#放回一次任务里看}

把刚才的维护动作放回同一次假设的告警查询超时任务，职责可以这样对照：

| 阶段 | Skill 的维护 | 记忆的维护 |
| --- | --- | --- |
| 开始排查 | 找到既有方法，确认适用范围 | 核对历史记录与当前请求 |
| 定位问题 | 发现步骤缺少一种查询模式 | 保存本次假设和对应证据 |
| 完成验证 | 用回放样本验证新增步骤 | 确认结论的适用条件 |
| 结束任务 | 在授权范围内更新并验证新版 | 入库带证据和复核条件的记忆 |
| 后续使用 | 记录步骤效果和误触发 | 记录命中、失效或反证 |
| 项目升级 | 修订、合并或替换旧方法 | 复核旧结论，处理检索和引用 |

执行任务和维护知识，开始时可以由同一个 Agent 分阶段做。任务多了，再考虑独立的维护 Agent 或定时任务。无论分给谁，验收都要看可复现的证据，换一个 Agent 点头并不算验证。

第一版可以先落在文件里。下面只是目录示意，实际发现路径和加载方式需要接入所用工具：

```text
project/
├── AGENTS.md                  # 项目入口、维护职责和权限边界
├── skills/                    # 已生效的操作方法
├── memory/                    # 可复核的事实与决策
└── governance/
    ├── index.yaml             # 标识、版本、状态、范围与依赖
    ├── candidates/            # 新产物和修改提案
    ├── evidence/              # 验证结果或证据引用
    ├── events/                # 使用反馈与状态变更
    └── archive/               # 已退出默认使用的历史版本
```

第一版先接通候选、验证、生效与反馈，再让反馈能触发修订和退出。每次变化留版本、留原因，改错了能回滚。

我希望交付时能看见：哪份 Skill 更新了，哪条记忆补了证据，哪些旧结论退出当前使用，哪些分歧还需要人决定。下一次打开项目，应该能接着工作，不用先清理上一轮留下的知识。

</section>
