title: Vibe Coding 卡住的不是写，是验
---

AI 会不会写代码，这个问题已经没意思了。它写得很快。快到人跟不上读、跟不上审、更跟不上长期维护。

新项目里这事还好扛。空白仓库，上下文干净，写错了重来成本低。存量项目不一样。那里叠着历史原因、没写下来的约定、不敢删的兼容、线上修过的补丁。AI 看见的通常只有「当前代码 + 当前需求」。真正能不能改，取决于那些没写进注释的东西。

所以最危险的不是一个明显写错的 `if`。是一段看起来很合理的代码，把原来谁也没记录的规矩弄断了。

## 谁来审

以前大致是人写、工具查、人再看一眼。Vibe Coding 很容易滑成：AI 写、AI 审、AI 测、AI 修、再审一遍，然后合进去。

审的和写的如果吃的是同一份上下文，它们会共享同一种误会。比如代码里 `user == null` 就直接 return。两个模型都觉得空指针处理好了。产品真正要的可能是抛异常。于是写错、审核通过、整条链路都绿。

这不是模型笨，是自己证明自己。

## 别指望人把代码读完

有人说：那人认真 Review 不就行了。规模化之后这条路走不通。十分钟生成的东西，人可能要一小时才读明白。到十万行、百万行，逐行看是幻觉。

与其事后审 AI 写出来的每一行，不如先限制它能写什么。人去定意图和边界，机器去拒绝越界的改动。

## 先把项目讲清楚

别每次都让模型对着仓库猜架构、猜规范、再动手。把项目知识摊开：这是什么系统、哪段不能动、哪些接口要兼容、库怎么改、异常和日志怎么写、测试过什么算过。

有 `AGENTS.md`、有目录清楚的文档、有按任务拆开的 skill，本质上就是给模型一块带围栏的场地，而不是一片空地。

## 质量变成门禁，不是建议

编译、单测、集成、静态检查、架构规则、安全扫描，过不了就不能合。机器必须能说不。AI Review 如果只是「建议」，在合入压力面前等于没有。

高风险改动再拉人进来。不是人去读所有 diff，是人只看越界的那一部分。

## 别让几个 Agent 重复评价「写得好不好」

与其再挂一个 Reviewer 用差不多的眼光看同一段代码，不如拆开问具体问题。测试的问：需求有没有被测到。安全的问：有没有新风险。架构的问：有没有踩项目自己的规矩。数据库的问：变更能不能兼容。

问题越具体，越不容易一起瞎。

还有一层更硬：外部事实。很多错只有跑起来才知道。改计价就拿历史订单回放，新旧结果对着看。这时不再是「模型觉得对」，而是「这批数据上结果对得上」。

## 顺序也该倒过来

需求进来，先分析影响面，再出修改计划和验证方案，先补测试，再改代码，跑验证，对比结果，最后才提交。也就是 Plan → Test → Code → Verify。不是先写一堆，再请人（或另一个模型）看一眼。

人的角色会往上走：定目标、定约束、定架构和风险边界。模型在边界里实现和举证。举证过不了，就不能当它做对了。

## 一句收住

Vibe Coding 真正稀缺的不是生成，是验证。生成成本掉下去了，理解和验证的成本没有一起掉，存量系统就会迅速堆债。破局不是加人盯代码，而是约束、自动验证、彼此独立的检查，再加上高风险才进人工。谁能让模型在几十万、几百万行的老系统里持续改、还不失控，谁才把这件事做成了工程。
