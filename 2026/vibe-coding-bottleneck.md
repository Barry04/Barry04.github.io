title: 在存量项目中 Vibe Coding，如何更好让 Agent 写出优质代码
---

AI 会不会写代码，这题可以收了。它写得很快。快到我读完 diff 之前，下一轮已经又改完了。

新仓库还好说。目录干净，约定都在眼前，写砸了重来也不可惜。

老项目不是这样。代码下面压着当年为什么这么写、哪段接口不能动、谁随手打的补丁、线上炸过一次所以谁都不敢删的分支。模型看见的通常只有「当前文件 + 当前需求」。能不能动，取决于那些没人写进注释的东西。

我怕的不是一个明显写错的 `if`。是那段读着挺顺的改动，把一条没人记下来的规矩弄断了。过两个月才在生产上冒出来，那时已经说不清是谁改的。

![一个写着“当前代码”的抽屉柜下，藏着许多旧规则与维修记录。](../assets/vibe-coding-bottleneck-illustrations/01-hidden-rules.png)

模型默认只看得见柜子上面那张卡。真正让人不敢乱动的，常常塞在下面几层。

## 审的和写的是同一张嘴

以前好歹是人写、工具扫一眼、人再看。现在很容易变成：它写，它审，它测，它修，再审一遍，合进去。

流程看着齐全。写的和审的如果吃同一份上下文，误会也会共享。

```java
if (user == null) {
    return;
}
```

写的说空指针处理好了。审的说对，确实判了 `null`。产品要的可能是抛异常，不是悄悄 `return`。两边都点头，检查全绿，线上用户没了。

这不是模型笨。是自己给自己盖章。

![同一个人写完答案，又拿同一枚章给自己打勾；旁边的证据袋还没有打开。](../assets/vibe-coding-bottleneck-illustrations/02-self-review.png)

让模型多审一次不一定没用，但它不等于独立验证。真正能反驳它的，是一份不同来源的证据：跑出来的结果、可复现的测试、或知道业务后果的人。

## 别指望人把 diff 读完

“人认真 Review 不就行了。”说着轻松。十分钟吐出来的东西，我可能要一小时才读明白。代码一多，逐行看就是安慰自己。十万行、百万行更别提。

与其事后盯每一行，不如先划它能写什么。意图和边界人来定；越界的改动，机器直接挡回去。

## 我现在比较信的做法

先把项目讲明白。别每次都让模型对着仓库猜。

这个系统是干什么的、哪段动不得、哪些接口要兼容、库怎么改、异常怎么抛、日志怎么打、怎样才算测过，应该摊开写下来。

![把“这个系统”“怎么改”“怎么验”三张卡钉在工作台前，危险区域另挂红色标签。](../assets/vibe-coding-bottleneck-illustrations/03-project-map.png)

`AGENTS.md` 可以是一张总目录：先告诉 Agent 从哪里开始看。架构、业务规则、编码约定、库表说明、部署风险放进能分别阅读的文档。按任务做的 Skill，再讲清楚这次具体怎么做。

文档说清为什么不能动，Skill 说清这次怎么动。这样模型不是站在空地里自由发挥。

### 质量得能说不

编译、单元测试、集成测试、静态检查、安全扫描、架构规则，这些东西的价值不在于报告多漂亮，而在于它们可以把改动挡回去。

测试挂了、规则破了、架构踩线了，不许合。真高风险再叫人来看。那种“建议你注意一下”的 AI Review，赶工的时候等于没有。

不要让几个 Agent 重复说“写得不错”。把问题拆开问：

- 测试只问：需求有没有真的测到？
- 安全只问：有没有引入新洞？
- 架构只问：有没有踩自己的边界？
- 库表只问：变更能不能兼容旧版本？

问得越死，越不容易一起瞎。

### 跑起来才算数

用代码解释代码，很多错发现不了。改计价别只盯着 `calculatePrice()`。拿一批历史订单回放，新旧结果对着看。

我想要的不是“它觉得对”，是这批数据对得上。

![把旧订单送进测试装置，左右两张结果单被放在一起，用放大镜核对。](../assets/vibe-coding-bottleneck-illustrations/04-real-evidence.png)

代码可以解释自己为什么看起来合理；运行结果会告诉你它到底有没有把旧用户弄坏。后者才算证据。

### 老项目里，顺序倒过来

需求来了先别写。

先看影响面，再写计划和验证办法；测试先落下，再改代码；跑一遍，对结果，最后才提交。

![老机器还没动手修，旁边已经摊开检查单、测试纸和量尺；螺丝刀还放在一边。](../assets/vibe-coding-bottleneck-illustrations/05-before-code.png)

这听着慢，其实是在省返工。老项目里最贵的不是多花十分钟想清楚，而是把一条隐性规则带到生产上，再花三天捞人。

可以把顺序压成一句：

```text
先看 → 先验 → 再改 → 对结果 → 提交
```

不是先堆一版，再请另一个模型看一眼。

人往上走：目标、约束、架构、风险。模型在框子里实现，还得拿出证据。证据过不了，就当它没做对。

## 收住

生成已经便宜了。读懂和验过，没有一起变便宜。老系统会很快堆出一堆说不清的债。

我不指望加人盯 diff。约束、自动验证、彼此不问同一句话的检查，再加上真危险才叫人。改代码就得给得出能核对的东西，别让我凭感觉信它。

谁写得快以后没那么值钱。谁能在几十万、几百万行的老代码里持续改、还不把系统改散，才算把这件事做成了工程。
