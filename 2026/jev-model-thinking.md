前两篇都在讲同一件事：[存量项目里怎么让 Agent 别改散](./vibe-coding-bottleneck.md)、[Skill 攒多了怎么管](./skill-lifecycle.md)。写的时候我一直有个说不清的别扭感：这些做法像是被问题逼出来的补丁，一个接一个，看不见边。

最近看 JEV 的时候，那种别扭感对上了。

先交代一句：下面的 JEV 理解是我读文档、看 demo 之后的个人复述，不是官方定义。我想说的本来也不是这个系统有多强，而是一个更朴素的观察——

> 从 prompt，到 harness、skill，再到 JEV 这类决策运行时，可能不是四个产品，而是同一条路上的四段台阶。

它们回答的问题越来越晚，也越来越具体：**先告诉模型要注意什么，再帮它把注意力的预算管好，接着把人的经验固化给它，最后替它在岔路口把证据摆齐。**

## 一、先说我把 JEV 理解成了什么

我看到的 JEV 大致是这样一套东西：把「判断」从聊天变成一条可执行、可追踪的路径。

模型最擅长的事是生成——你给一段上下文，它顺着往下写。可模型本身没有状态，它一轮一轮地重新读上下文，`think` 只是文本，`change` 只是动作。但真实任务的样子是：

```text
查日志 -> 判断是不是缓存问题 -> 查缓存 -> 判断是不是热点 -> 查热点 -> 判断修复方案
```

这条链有三个特点：**步骤之间有依赖**（顺序错了结果就废了）、**每步都可能回退**（查到一半发现方向不对）、**最后要能解释**（凭什么做这个决定）。这三点，恰好都不是「更长的 prompt」能解决的。

所以我的理解是：JEV 干的是把「决策」这个东西本身当成被管理对象的活。它的核心不是让模型更聪明，是替模型把这几件事管住：

- **记着走到哪了。** 上下文会截断，会话会丢，但走过的路径应该在。
- **知道哪条路已经验证过。** 同一个决策点，别每次重新猜；上次怎么判断的、结果对不对，存下来。
- **知道哪个活可以并行、哪个必须等。** 排查可以并发跑三条线，修复必须等结论。
- **把证据链补齐再让人拍板。** 不是「我建议回滚」，而是「三条证据指向这三个改动之一，请你选」。

用一句话概括：**它管的是决策的状态，不是对话的状态。**

一个很硬的证据是 Claude Code 自己的轨迹：最早靠一个几百字的系统提示词，后来变成 `AGENTS.md` 加 Skill 目录，现在长成了一套带子代理、权限门禁和校验环节的 harness。这不是谁拍脑袋设计的，是一代代撞到墙上之后往外挪的结果。

再往前看一层，这个逻辑还成立。ReAct 当年也只是论文里的实验技巧——把思考和行动拆成两段交替；今天它成了所有 Agent 框架的地基。**行业不是先画出架构图再实现，而是先把某个技巧磨成标准件，再拿它去搭下一层。**

## 三、把台阶拆开看，能看到什么

三代做法摆在一起，会看到一张很整齐的表：

| | Prompt | Harness / Skill | JEV 这类决策运行时 |
|---|---|---|---|
| 主要解决什么 | 让模型知道该往哪走 | 让模型按对的方法走 | 让模型在岔路口有依据地走 |
| 载体 | 一次对话里的文字 | 文件、目录、脚本、门禁 | 路径、分支、回退、证据链 |
| 谁能改 | 会说话的人都能改 | 懂项目的人能改 | 需要能定义风险和验证的人 |
| 主要成本 | 反复调措辞的隐形时间 | 文档维护、Review、回归 | 建模正确性、可调试性 |
| 出问题时 | 说不清为什么这次不行 | 规则过期了还在执行 | 决策链本身要能解释、能追责 |
| 失败的样子 | 结果时好时坏 | 灵活任务被框死 | 路径看着完整，结论是错的 |

最后一行是我最在意的。

Prompt 时代的失败很容易发现——结果不对，重写一遍。Harness 时代的失败开始变得隐蔽——规则过期了，但文件还在，Agent 还在很笃定地执行。而决策运行时的失败是最难看的：一条路径从头走到尾，每一步都有理由，可结论是错的。

而且在决策运行时的语境里，「幻觉」这个词不太够用了。模型每个字都基于真实证据，环节也没有编造，问题出在一个环节的标注是错的：它以为「没触发熔断」等于「系统健康」。这种错不靠更长上下文发现，它需要的恰恰是第三层的能力——**去问「这个判断是怎么得出的」，然后找到那个被默认成立的假设。** 我猜这也是为什么这类系统会把「可调试」看得比「更聪明」更重。

## 五、给这条曲线画个函数

我试着把这条演化压成一个式子：

```text
Agent 的可用性 = 模型能力 × 上下文组织
```

用最省事的方式来理解这个「×」：先把模型能力看成「单轮能做多好」，把上下文组织看成「这条任务链能不能被完整地交给它」。

那么三代做法的差别，就可以用两个极端来推：

- 上下文组织接近零 —— 也就是零上下文。模型再强，也不知道这个仓库的规矩，只能瞎猜。乘积为零。
- 模型能力接近零 —— 上下文组织到极致，也是一具没有判断力的骨架，只能照章办事。

**任何一边单独登顶，乘积都不大。**

这也能解释 Claude Code 那种演进路径为什么是那个样子：模型能力在自然增长（同一句提示词，今年比去年好用），同时工程侧在拼命加东西（文档、Skill、门禁、校验）。两个因子是乘法，所以两边都不能停。

这个×还决定了投入该怎么分配。加法的话，一边拉满就够了；乘法的话，补短板才是唯一有意义的事。而现在这个阶段，短板明显不在模型那边——**模型每几个月涨一截，上下文组织却还是手工活。** 这大概就是为什么大家都在往 harness、skill、决策运行时上使劲。

## 六、主线是「把不确定性挤出流程」

还有一个角度我越想越觉得成立。

三代做法，本质都在干同一件事：**把一个靠模型随机发挥的过程，改成一条更确定的路径。** Prompt 是软的——同一个意思换个说法，结果就不同。Harness 硬了一半——边界写死，越界挡回。决策运行时想让整个链路可重放——同一输入，同样的判断。

生物上有「前馈」和「反馈」两个词，我觉得用来区分这三代挺合适：

- 前馈（anticipate）：规则是提前定好的，算的是「输入像不像我认识的那类问题」。Workflow、硬编码规则属于这一类。
- 反馈（observe then decide）：听结果，根据观察调整。ReAct、Agent Loop 属于这一类。

这两件事前两代一直在打架：纯前馈的系统稳定但僵，能应对的问题集合是封死的；纯反馈的系统灵活但飘，每次都得重新求证一遍。

我看 JEV 这类东西有意思的地方，是它试着换一条路解决这个矛盾：**把「稳定」和「灵活」拆开放，让稳定来自决策结构，灵活来自上下文。**

结构是确定的——有几个关键判断、什么条件下必须验证、哪些并发哪些串行、什么时候必须停下来问人。走哪条路是灵活的——同一个决策点，走的可能是上次已验证的路径，也可能是新收集的证据。

这么一来，稳定性不再靠「边界写得多死」，灵活性也不再靠「模型自己聪明」。这也正是 skill 和后端工程能插进来的地方：**你写的每一个 skill，都是在往这个结构里填一个「这类判断该怎么做」的模板。**

## 七、它不是替代前三层，而是重新安排它们的位置

我一开始以为第四层是「更高的一种 Agent」，后来觉得这个理解不对。

正确的读法可能是：控制点往外挪一层，前三层本身的性质也变了。

- **Prompt 从「人写的话」变成「运行时组装的上下文」**——不再是我一次写完，而是根据当前走到哪一步动态拼出来。
- **Harness 从「静态规矩」变成「路径上的检查点」**——不是文档里写「要测试」，而是在这条链的第几步必须过测试，过不了就停。
- **Skill 从「说明书」变成「决策模板」**——不只是「这类活怎么做」，还有「做到这一步时，什么情况下该换个方向」。

所以往上一层，底下那层不是被取代，是被重新定义了一遍。这也是我看好这类方向的原因：它给已有的东西重新安排了位置。

## 八、我自己觉得还没着落的地方

写到最后，更想说说我看不明白的部分。

**第一，决策的粒度。** 太粗没意义，太细就是「第二步要选 B」的另一种硬编码，模型被降级成执行器。这个粒度怎么定，跟团队和任务强相关，很难推广。

**第二，谁能改决策规则。** 改一个 prompt 不影响过审，改一段判断逻辑可能影响线上行为。它该走什么流程？有没有灰度？谁来签字？这些问题现在基本没有答案。

**第三，怎么衡量它真的有用。** 按输出质量评分太主观。也许该看的是另一类数字：同一个任务重跑两次，决策链一致率有多高；上次验证过的路径被复用了多少次；回退率是升还是降。**如果不比「每次重新猜」更确定，那这套东西的价值就只是好看。**

**第四，它会不会把模型锁死。** 强路径加验证，短期确实更稳。可模型一旦升级，旧路径可能反而拖后腿——它把上一代模型的能力上限当成了这一代的约束。这可能就是 Skill 腐化在决策层的版本：**比过期的文档更麻烦，因为过期的是路径。**

说到这儿，其实又回到了前两篇。那篇讲的是 Skill 要有进门和出门，这篇讲的是同一个道理往上走了一层：**决策路径同样需要一套生命周期。** 产生不等于采纳，验证过不等于一直有效，被替换的路径该有地方退休——不然它们会安静地待在链路里，等着把 Agent 带到上一次正确、这一次错误的地方。

## 收住

如果把这条线连起来看，其实挺简单：

```text
prompt  ->  告诉模型该注意什么
harness ->  帮模型把注意力管好
skill   ->  把人的经验固化下来
决策    ->  让模型在岔路口有依据地走
```

每一步都在回答上一个不能解决的问题。不神秘，也不玄。

真正值得警惕的不是模型不行，而是模型很快；工程和理论那一边慢一拍，就只能靠「多写几句提示词」和「让模型再检查一遍」硬撑。JEV 这类东西让我觉得踏实的地方在于，它承认了一件不太体面的事：

> 模型可以很强，但把它接到真实世界里，剩下的工位得有人去填。

我不是 JEV 的作者，也摸不到生产环境。这篇只能算站在外面，对着一条我刚刚看懂的曲线做的一点推演。如果这条曲线是对的，那接下来会遇到的问题大概也能提前知道——只不过问题会出现在哪一层，现在还说不准。
